# Deploying PaiPai

This guide takes PaiPai from your laptop to production:

| Piece         | Where                           | Address                                        |
| ------------- | ------------------------------- | ---------------------------------------------- |
| Website       | **Vercel**                      | `https://paipai.priyanshusingh.co.in`          |
| API           | **Render** (or any Docker host) | `https://api.paipai.priyanshusingh.co.in`      |
| Database      | **Neon** (already set up)       | —                                              |
| Email         | **Resend** (already set up)     | —                                              |
| Receipts      | **Cloudflare R2** (optional)    | `https://receipts.paipai.priyanshusingh.co.in` |
| Android / iOS | **EAS Build** (Expo)            | APK / Play Store / App Store                   |

These addresses are already filled in where they aren't secret: [`render.yaml`](../render.yaml), the website's production build ([`apps/web/next.config.ts`](../apps/web/next.config.ts)), the app builds ([`apps/mobile/eas.json`](../apps/mobile/eas.json)) and the cron workflow. Keys and where to get them are in [SETUP-KEYS.md](SETUP-KEYS.md).

### DNS records

Add these at the DNS provider for `priyanshusingh.co.in` (the same place where you added the Resend records):

| Type    | Name         | Value                                 | For     |
| ------- | ------------ | ------------------------------------- | ------- |
| `CNAME` | `paipai`     | the value Vercel shows (section 3)    | website |
| `CNAME` | `api.paipai` | `paipai-api.onrender.com` (section 2) | API     |

Both providers issue the HTTPS certificates automatically once the records resolve, which usually takes a few minutes.

---

## 0. The one rule: web and API on the same domain

The API sets the session cookie, and the website's route guard reads it. Browsers only share a cookie between hosts under one domain you control, so:

- ✅ `paipai.priyanshusingh.co.in` + `api.paipai.priyanshusingh.co.in`, with `COOKIE_DOMAIN=.paipai.priyanshusingh.co.in`
- ❌ `paipai.vercel.app` + `paipai-api.onrender.com`: login will loop forever

The API checks this at startup. With a wrong setup it refuses to boot and tells you exactly what's wrong (see [Troubleshooting](#troubleshooting)).

## 1. Database (Neon)

You already have a Neon project. For production, either reuse it or create a separate branch (Neon → **Branches → Create branch** `production`) so test data stays out.

Apply migrations to the production database from your machine:

```bash
# PowerShell: $env:DATABASE_URL="postgresql://...pooler.../paipai?sslmode=require"; pnpm db:migrate; pnpm db:seed
DATABASE_URL="postgresql://...pooler.../paipai?sslmode=require" pnpm db:migrate
DATABASE_URL="postgresql://...pooler.../paipai?sslmode=require" pnpm db:seed
```

Use the **pooled** connection string (`-pooler` in the host). Run `pnpm db:migrate` again whenever a release adds a migration (files in `packages/db/drizzle/`).

## 2. API on Render

### 2.1 Create the service

1. Push this repo to GitHub (done).
2. Render dashboard → **New → Blueprint** → pick the repo. Render reads [`render.yaml`](../render.yaml) and creates `paipai-api` in **Singapore** (closest to India and to Neon `ap-southeast-1`).
3. The addresses (`BETTER_AUTH_URL`, `WEB_URL`, `COOKIE_DOMAIN`) and `EMAIL_FROM` are preset in the blueprint. Render asks only for the secrets:

| Variable               | Value                                           |
| ---------------------- | ----------------------------------------------- |
| `DATABASE_URL`         | Neon pooled connection string                   |
| `GOOGLE_CLIENT_ID`     | same as local                                   |
| `GOOGLE_CLIENT_SECRET` | same as local                                   |
| `RESEND_API_KEY`       | same as local (or a separate production key)    |
| `R2_*`                 | your R2 values, or leave empty to hide receipts |

`BETTER_AUTH_SECRET` and `CRON_SECRET` are generated by Render automatically. Don't reuse your local ones.

What the blueprint does:

- **Build:** installs only the API and its workspace packages, then bundles it with tsup.
- **Start:** `NODE_ENV=production node dist/index.js` (production checks on).
- **Health check:** `/health/ready`, which also pings the database. A deploy only goes live once it passes.

### 2.2 Custom domain

Render → `paipai-api` → **Settings → Custom Domains → Add** `api.paipai.priyanshusingh.co.in`. At your DNS provider add the `CNAME` it shows (`api.paipai` → `paipai-api.onrender.com`). Render issues the HTTPS certificate automatically.

Check it:

```bash
curl https://api.paipai.priyanshusingh.co.in/health/ready
# {"ok":true,"db":"up","latencyMs":...}
```

### 2.3 Free plan vs paid

The **free** plan sleeps after ~15 minutes without traffic. The first request after that takes up to a minute, and the in-process scheduler doesn't run while it's asleep. That's fine to try things out. For daily use switch the service to a paid instance (`plan: starter` in `render.yaml`) so it stays awake.

### 2.4 Recurring transactions in production

Two runners exist, and running both at once is safe (rows are locked with `FOR UPDATE SKIP LOCKED`, so nothing is created twice):

- **In-process scheduler** (default): runs every 10 minutes while the API is awake.
- **Cron endpoint**: `POST /api/cron/recurring` with `Authorization: Bearer $CRON_SECRET`.
  [`.github/workflows/recurring-cron.yml`](../.github/workflows/recurring-cron.yml) calls it every 30 minutes. To turn it on, open GitHub → repo → **Settings → Secrets and variables → Actions**:
  - **Secret** `CRON_SECRET`: copy the value from Render → Environment.
  - **Variable** `API_URL` is optional; it defaults to `https://api.paipai.priyanshusingh.co.in`.

  Use this on the free plan, or on serverless hosts with `DISABLE_SCHEDULER=1`.

### 2.5 Alternative: Docker (Fly.io, Railway, a VPS…)

```bash
docker build -f apps/api/Dockerfile -t paipai-api .
docker run -p 8787:8787 --env-file .env.production paipai-api
```

The image runs as a non-root user, has a `HEALTHCHECK`, and contains only production dependencies. Set the same variables as in the table above. The host must give you HTTPS on a subdomain of your web domain.

## 3. Website on Vercel

1. Vercel → **Add New → Project** → import the repo.
2. **Root Directory:** `apps/web`. Vercel detects Next.js and pnpm, and installs from the repo root (keep "Include files outside the root directory" enabled; the site uses `packages/shared`).
3. **Environment variables:** none needed. Production builds on Vercel use these automatically (see `next.config.ts`); set them in Vercel only to override:

| Variable               | Value                                     |
| ---------------------- | ----------------------------------------- |
| `NEXT_PUBLIC_API_URL`  | `https://api.paipai.priyanshusingh.co.in` |
| `NEXT_PUBLIC_SITE_URL` | `https://paipai.priyanshusingh.co.in`     |

They are baked in at build time, so **redeploy** after changing them.

4. **Deploy**, then **Settings → Domains → Add** `paipai.priyanshusingh.co.in` and add the DNS record Vercel shows.

> Vercel preview deployments (`*.vercel.app`) can't sign in, because of the cookie rule in section 0. Test on the real domain, or add a `preview.paipai.priyanshusingh.co.in` domain and list it in the API's `EXTRA_TRUSTED_ORIGINS`.

## 4. Google sign-in for production

Google Cloud Console → **APIs & Services → Credentials** → your **Web** OAuth client:

- **Authorized JavaScript origins:** add `https://paipai.priyanshusingh.co.in`
- **Authorized redirect URIs:** add `https://api.paipai.priyanshusingh.co.in/api/auth/callback/google`

Keep the localhost entries for development.

**OAuth consent screen → Publish app** (move from "Testing" to "In production"). PaiPai only asks for `openid`, `email` and `profile`, so Google doesn't require a verification review. While the app is still in Testing, only the test users you listed can sign in.

The same client also handles mobile sign-in, because the app goes through the API (section 6).

## 5. Smoke test

1. Open `https://paipai.priyanshusingh.co.in` → **Get started** → sign up with email. The code arrives from your Resend domain.
2. Add an expense with **N**, open Analytics, export a CSV.
3. Log out, then **Continue with Google**.
4. Render logs show JSON lines like `{"msg":"http.request","status":200,...}`. Each response has an `X-Request-Id` header for tracing.

## 6. Mobile app with EAS Build

### 6.1 One-time setup

```bash
npm install -g eas-cli
eas login                      # free Expo account: https://expo.dev/signup
cd apps/mobile
eas init                       # creates the Expo project and writes extra.eas.projectId into app.json
```

Commit the `app.json` change. The `projectId` is also what turns on **remote push notifications** (budget alerts).

The `preview` and `production` profiles in [`eas.json`](../apps/mobile/eas.json) already point the app at `https://api.paipai.priyanshusingh.co.in`.

### 6.2 Android

```bash
eas build --profile preview --platform android      # installable .apk, share the link
eas build --profile production --platform android   # .aab for the Play Store
```

**Push notifications on Android** need Firebase Cloud Messaging credentials:

1. Firebase console → create a project → add an Android app with package `com.paipai.app`.
2. **Project settings → Service accounts → Generate new private key** (JSON).
3. `eas credentials` → Android → production → **Google Service Account → FCM V1** → upload the JSON.

Keep that JSON file out of the repo (it's a secret).

### 6.3 iOS

You need an **Apple Developer Program** membership.

```bash
eas build --profile production --platform ios   # EAS creates certificates and the push key for you
eas submit --platform ios                       # upload to App Store Connect / TestFlight
```

### 6.4 What changes on a real build vs Expo Go

- **Google sign-in** works: it goes through `https://api.paipai.priyanshusingh.co.in` and returns to the app via the `paipai://` link.
- **Push budget alerts** work once `projectId` is set (and FCM on Android).
- **Face ID** uses PaiPai's own permission text instead of Expo Go's.
- Release builds talk only to `EXPO_PUBLIC_API_URL`, and it must be `https://`.

### 6.5 Store listing

`eas submit --platform android` uploads to Google Play (needs a Play Console account and a service-account key). Both stores need a **privacy policy URL** (PaiPai stores email, name and the transactions you enter) and a **data deletion** path: Profile → Delete account removes the user and everything they own.

## 7. Releasing updates

- **API / website:** push to `main`. CI ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) runs format, lint, typecheck, tests, builds, the mobile bundle and the browser E2E. Render and Vercel deploy automatically.
- **Database changes:** `pnpm db:generate` → commit the migration → run `pnpm db:migrate` against production **before** the API deploy that needs it.
- **Mobile:** bump `version` in `app.json` for store releases (build numbers auto-increment), then `eas build` again.

## Troubleshooting

| Symptom                                                      | Cause / fix                                                                                                                                                |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Render deploy fails with `Invalid production configuration`  | The log lists each problem, e.g. `WEB_URL must be an https:// URL` or `COOKIE_DOMAIN must cover both …`. Fix those variables and redeploy.                 |
| Login succeeds, then bounces back to `/login`                | Cookie not shared: check `COOKIE_DOMAIN` (leading dot) and that web and API are subdomains of the same domain.                                             |
| Browser console shows a CORS error                           | `WEB_URL` on the API must exactly match the site's origin (`https://`, no trailing slash). Extra origins go in `EXTRA_TRUSTED_ORIGINS`.                    |
| Google: `redirect_uri_mismatch`                              | Add `https://api.paipai.priyanshusingh.co.in/api/auth/callback/google` to the Web OAuth client (section 4).                                                |
| Google: "Access blocked: app not verified / only test users" | Publish the OAuth consent screen (section 4).                                                                                                              |
| No OTP email                                                 | Check the Resend dashboard → Logs. `EMAIL_FROM` must be on your verified domain.                                                                           |
| First request takes ~1 minute                                | Render free plan waking up. Use a paid instance.                                                                                                           |
| `/health/ready` returns 503                                  | API can't reach Neon: check `DATABASE_URL` and that the Neon project isn't suspended or out of quota.                                                      |
| Mobile release build can't connect                           | Check `EXPO_PUBLIC_API_URL` in `eas.json` for that profile, and that `https://api.paipai.priyanshusingh.co.in/health` responds. Rebuild after changing it. |
| No push notifications                                        | Needs a real build (not Expo Go), `eas init` projectId, and FCM credentials on Android. Notification permission must be allowed on the phone.              |
| Receipts / profile photo option missing                      | All five `R2_*` variables must be set on the API.                                                                                                          |
